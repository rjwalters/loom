# Fleet-Captain Dispatch: The Captain Assigns, Workers Ask (Issue #12447)

This is the Phase 0 spec for fleet-captain dispatch. It replaces "every host gathers every repo and draws independently, then races for the claim" with **one assigner**: a worker's tick asks the fleet captain for its next assignment, and the captain answers from a fleet-wide work queue it refreshes about every 10 minutes.

**Status: Proposed.** This doc is the whole deliverable of #12447. Merging it is not approval to build. Phases 1-3 (section 13) are filed at `loom:triage` only after the operator reviews this doc.

This is a repo-local design doc under `docs/design/`. It is never installed into consumer repos. The format follows [`work-finder-step-dispatch.md`](work-finder-step-dispatch.md).

**Source SHA.** Citations are against `origin/main` at `ac3d55f76` (2026-10-16), or name a module and symbol, which do not drift. Paths without a prefix are under `loom-daemon/src/`. Paths under `defaults/` and `docs/` are written in full.

## 1. Fixed input: operator direction

From the attended session of 2026-10-16, and not reopened here:

1. **Invert the logic.** The fleet captain assigns work. Instead of a claims system there is a fleet mode where each worker asks the captain for its next assignment.
2. **The captain sees the fleet config**, so it can decide which host may take which item.
3. **The captain keeps a queue of work**, refreshed about every 10 minutes, to cut GitHub load further.
4. **The Matrix peer-claim channel becomes low priority** (2am#4566). It would only narrow the race.
5. **Prioritized** (operator comment on #12447). Phase 1 shares one wire contract across #12449 (captain server, `fleet-dispatch serve`), #12450 (worker client, failing open with hysteresis) and 2AMLogic/2am#4976 (tailnet ACL, captain unit, a per-host flag on 2 workers as the A/B group).

## 2. Problem

Measured on 0.19.1172 (figures from the issue, not re-measured here):

| Measure | Value |
|---|---|
| Step draws that ended `claim_lost` | 37% |
| Slot occupancy at cap 40 | 25-55% |
| CPU | 15-18% |
| Forge gather | once per host per tick |

Three effects, one root cause (each host decides alone):

1. **The claim race.** Every host draws from the same actionable items by the same weighted draw (`step_dispatch/item_draw.rs`), so hosts pick the same item and all but one lose. The loser has already paid for a claim subprocess.
2. **Ticks end before slots fill.** A lost claim ends up consuming the tick's pass budget. `MAX_PASSES_PER_TICK` and `MAX_FREE_CLAIM_LOST_PER_TICK` (`step_dispatch/tick.rs`) bound the draws, and #12448 raised them as a stopgap, then #12457 reverted it. Raising a limit treats the symptom; the collisions remain.
3. **Forge reads scale with host count.** The gather reads each repo per host per tick. This is what trips the writer and reader budgets. #12304 reduces each host's read to one mirror request, but N hosts still make N reads.

A peer-claim channel on Matrix narrows (1) only. One assigner removes it, and with a shared queue it removes (3) too.

## 4. Wire protocol

One request type, `next`, plus two reports. HTTP/1.1 JSON over the tailnet. The captain listens on a port from fleet-gitops config; the worker finds the captain by the `fleet.captain` host id resolved to its tailnet name. Every body carries `v: 1`; an unknown major version is refused (section 7 treats the refusal as unreachable).

### 4.1 `POST /v1/next`

Request:

```json
{
  "v": 1,
  "host": "host-7ec0fa4c",
  "request_id": "01J...",
  "free_capacity": {
    "slots": { "total": 40, "busy": 31, "by_role": { "builder": 12, "judge": 6 } },
    "disk_free_gb": 212,
    "cpu_load": 0.18
  },
  "constraints": {
    "max_assignments": 4,
    "roles": ["curator", "builder", "judge", "doctor", "champion"],
    "tools": ["ngspice", "klayout"],
    "exclude": [{ "repo": "acme/foo", "item": 41 }]
  }
}
```

- `host` is advisory. The captain takes the caller's identity from `whois` (section 9) and refuses a body whose `host` disagrees with it.
- `free_capacity` is what the worker measures live. The captain does not hold slot state. It cannot see disk or CPU, and a worker's own count is the only count that matches its spawn gate.
- `constraints.exclude` lists items the worker already knows it cannot take now (an item in its own registry, a recently refused one). It keeps the captain from handing the same item back in a loop.
- `max_assignments` is at most the worker's open step slots. The captain may return fewer.
- `request_id` makes the call idempotent: a retry with the same id returns the same assignments, not new ones (section 6.3).

Response `200`:

```json
{
  "v": 1,
  "request_id": "01J...",
  "assignments": [
    {
      "assignment_id": "01J...",
      "repo": "acme/foo",
      "item": 41,
      "kind": "issue",
      "step": "builder",
      "priority": "loom:important",
      "queue_etag": "W/\"9f2c\"",
      "queue_age_secs": 212,
      "lease": { "ttl_secs": 900, "renew_every_secs": 300, "expires_at": "2026-10-16T14:05:00Z" }
    }
  ],
  "queue": { "refreshed_at": "2026-10-16T13:50:12Z", "age_secs": 212, "source": "mirror" },
  "retry_after_secs": 30
}
```

An empty `assignments` is a valid answer ("nothing fits you now"), with `retry_after_secs`. It is not an error and it does not trigger fallback (section 7.2).

`step` is the closed set the step engine already uses (`step_role::StepRole`: curator, builder, judge, doctor, champion promote/merge, and so on). The captain chooses the item **and** the step, because the step follows from the item's state, exactly as the local draw decides it today.

### 4.2 `POST /v1/report`

The worker reports what happened to each assignment. This is the only way the captain learns of a refusal or a stale entry.

```json
{ "v": 1, "host": "host-7ec0fa4c", "assignment_id": "01J...",
  "outcome": "spawned | refused | expired_unused",
  "reason": "stale | held | claim_lost | host_ineligible | no_capacity | ...",
  "observed": { "labels": ["loom:operator"], "state": "open", "head": "ab12..." } }
```

- `spawned`: the worker passed its pre-check, took the forge claim, and started the step. The captain marks the item *assigned* and starts expecting renewals.
- `refused`: the worker's pre-check (section 8.3) or the claim itself failed. The captain drops the item from the queue (for `stale`, `held`) or re-queues it (for `no_capacity`, `host_ineligible`), and records `observed` as fresher than its queue entry.
- `expired_unused`: the worker will not use the assignment (shutdown, slot taken by a higher-priority local step). The captain re-queues immediately.

### 4.3 `GET /v1/state`

Read-only, for `loom-daemon status` and the dashboard: queue age, size per repo, assignments outstanding per host, last refresh cost. Never read by a dispatch decision.

### 4.4 Errors

Status codes: `400` malformed, `401` caller not identified, `403` caller not a fleet host, `409` version mismatch, `429` with `retry_after_secs`, `5xx` captain fault. Only a `200` is an answer; everything else counts as "captain unavailable" for section 7.

## 5. Scheduling policy

The captain applies the same policy the local draw applies today, once, fleet-wide. Where the local draw is a seeded weighted draw per host, the captain's is a deterministic pick with the same weights, because there is no longer a seed to keep in agreement across hosts.

### 5.1 Priority

Order of tiers, as for the local draw and the Builder prompt:

1. `loom:very-important`, then `loom:important`. Order only; an item still needs the labels its step requires.
2. Everything else, by the draw weight below.

Hard exclusions never enter the queue: `loom:operator`, `loom:frozen`, `loom:blocked` unless self-released, and the hard-exclusion labels (`defaults/scripts/hard-exclusion-labels.sh`), plus any `extraSkipLabels` in the repo's workFinder config. The captain applies the same skip set as the local finder so the two never disagree.

### 5.2 Weight within a tier

`actionable x priority x stage-age`, the ruling of `work-finder-step-dispatch.md` section 1, unchanged: age measured from entry into the current stage, creation age until a stage-entry time is known. The captain does not add a stage term or per-stage quotas.

The weighted draw is replaced by **highest weight first among the items that fit the asking host**, with ties broken by the item's age. Randomness existed to keep hosts from converging on one item. With one assigner that need is gone, and determinism makes the schedule replayable from the queue snapshot (section 10).

### 5.3 Per-host fit

An item fits a host when all of the following hold. They are read from the fleet config (`fleet_store`) and the item, not from the worker's request, except capacity:

- the host serves the item's repo (registered repos);
- the host runs the step's role (roles per host);
- the host has the tools the item needs (`<!-- loom:requires-... -->` capability markers, `capability.rs`);
- the host satisfies the item's host pin if it has one (`loom:host:<id>`, `<!-- loom:requires-host=<id> -->`, `host_affinity.rs`);
- the host's reported `free_capacity` has an open slot for that role, and disk above the per-step floor.

An item that fits no currently-asking host stays in the queue and ages. It is not an error.

### 5.4 Fairness

- **Per-repo spread.** At most `K` outstanding assignments per repo per host (config; default the local finder's per-repo cap), so a deep repo cannot fill one host while the others starve.
- **Per-item exclusivity.** One outstanding assignment per item, fleet-wide. This is the property that removes `claim_lost`.
- **Small-repo protection.** Item-first drawing (`work-finder-step-dispatch.md` section 1, ruling 1; #12185) exists because small repos took 31% of draws. The captain keeps it: the unit being weighted is the item, not the repo.
- **Starvation.** An item's weight grows with stage-age, so an item that no host currently fits cannot be starved by newcomers. `step-slots-idle` and `step-dispatch-stalled` (`work-finder-step-dispatch.md` section 7) stay the watch, plus `captain-no-assignments` (section 10).

## 6. Leases, TTL and re-assignment

### 6.1 The forge lease stays the record

The assignment is **a permission to claim, not a claim.** After `/v1/next` the worker still performs today's claim path: flip the label (`loom:issue` to `loom:building`, and so on), write the lease comment (`<!-- loom:lease host=... sweep=... -->` or the PR-phase marker family in `lease-record.md`), start the renewer. The forge lease remains authoritative for "who is working this item", for the Judge and Champion, for `check-claim`, for reclamation, and for every non-fleet-mode host. The captain's table is a hint plus a scheduling index, never the source of truth.

This is what keeps the design safe. If the captain is wrong, stale or gone, the worst case is today's behaviour: a worker loses a claim race on the forge and passes.

### 6.2 Assignment lease

Each assignment carries `ttl_secs`, the same TTL model as the forge lease (default 900, from `LOOM_LEASE_TTL_MINUTES`), and `renew_every_secs`.

- **Before `spawned`.** The assignment lives `ttl_secs`. If no `report` arrives, the captain treats it as `expired_unused` and re-queues the item. The window covers the worker's pre-check and claim; it is short on purpose.
- **After `spawned`.** The captain does not run its own renewal. It reads liveness from the forge lease comment's `updated_at`, the signal everything else already uses, polled from the mirror's change stream or the item's next queue refresh. A lease that stops being renewed is stale after the TTL by the existing reclamation rule (#6286), and the item returns to the queue as ordinary actionable work.
- **Re-assignment** after expiry goes to any fitting host, the original included. The forge claim-then-verify-order rule (#6287) already settles the case where the original worker is merely slow and comes back: a second claimant yields.

The captain therefore adds no liveness protocol. It reuses the forge lease for the one thing the forge lease is for.

### 6.3 Idempotence

`request_id` is kept for one assignment TTL. A retry (the worker timed out waiting for the answer) returns the same assignments. Without this a slow response would orphan the first set until it expired.

### 6.4 Captain restart

The captain's in-memory state is rebuildable:

- The queue is rebuilt from the next refresh (section 8) at start-up. The captain does not serve `/v1/next` until its first refresh completes, or serves from a persisted last-good queue marked stale (open item, section 15).
- The outstanding-assignment table is rebuilt from the forge: any item with a live forge lease is not assignable, whoever holds it. An assignment that was issued but had no `spawned` report is simply lost; its item re-enters the queue and may be handed out again. At worst one worker holds a permission another worker also received, and the forge claim settles it (section 6.1).

No persistent captain state is a requirement of this design.

## 7. Fail-open

**A captain outage degrades dispatch to current behaviour. It never stops dispatch.**

### 7.1 When the worker falls back

The worker's tick treats the captain as unavailable when `/v1/next` does not return a `200` within the **deadline** (config; default 3 s), returns `409` or `5xx`, cannot be resolved, or returns an `assignments` the worker cannot parse. It then runs the local draw for that tick, unchanged.

### 7.2 What is not a fallback

- An empty assignment list is an answer. The worker idles its open slots until `retry_after_secs`. It does not draw locally: that would reintroduce the race the captain exists to remove, from every worker at once.
- A `429` is an answer with a delay, not an outage.
- A refused assignment (section 8.3) is reported and the worker asks again.

### 7.3 Hysteresis

Flapping between modes is worse than either mode, because each flip re-opens the race for a tick. The client (#12450) therefore:

- enters **fallback** after `N` consecutive failed calls (default 3), and
- leaves it only after `M` consecutive successful calls (default 5) spread over a minimum dwell time (default 60 s).

While in fallback it still probes `/v1/state` or a bodyless `next` to know when the captain is back. The probe is cheap and carries no assignments.

### 7.4 Forge leases stay authoritative in every mode

In fallback the local draw is exactly today's, including the pre-claim guard (`loom-daemon forge check-claim`), the claim, and the lease. A fallback host and an assigned host contend for an item the way two local hosts do now, and the forge decides. This holds while some hosts are fleet-mode and some are not, which is what makes the Phase 1 A/B group (two workers, #4976) safe.

### 7.5 Break-glass

A per-host flag turns the client off (section 11, Phase 1). With it off, nothing in this design runs on that host: it never calls the captain, and the captain never learns it exists. This mirrors `forge.gateway` unset and `forge.mirror` unset.

## 8. The fleet queue: refresh, invalidation, staleness

### 8.1 Source: one read, not a second gather

The queue is fed by **#12304's single mirror read**, the same `GET /v1/mirror/worklist` that `discovery/mirror.rs` makes today for a host's tick. The captain runs that one request, conditional on the last ETag, on its refresh interval and builds the fleet queue from the resulting `TickSnapshot`-equivalent. It does not gather per repo.

When the mirror cannot answer for a repo (request failed, or `status` is not `ok`), the captain uses the same capped fallback tiers `discovery/fallback.rs` defines for the fleet (gateway, then `gh`), at the backstop pace. It does not invent a new read path, and it never reads through a writer tier ("There is never a writer tier").

Phase 2's forge read cost is therefore one worklist request per refresh interval for the whole fleet, replacing one per tick per host.

### 8.2 Refresh and invalidation

- **Interval.** About 10 minutes, set in fleet-gitops (`fleet.captainDispatch.queueRefreshSecs`, name provisional; clamped to a floor and a ceiling like `maxStalenessSecs`). The refresh is conditional, so an unchanged mirror costs a `304`.
- **Early invalidation.** The captain subscribes to the mirror's change stream (`forge_mirror/wake.rs`, `GET /v1/changes`). A change for a repo marks that repo's queue entries *suspect* and triggers an early, conditional refresh of the worklist, under a spacing floor. ADR-0021's invariants hold as written: **a change is a nudge, never a command**. It carries routing hints only, and no title, number, label or state from it reaches a decision. The decision comes from the refreshed worklist.
- **Polling is the floor.** A dead stream or an unset mirror leaves the interval as the only refresh. The failure mode is latency, never a wrong assignment.
- **Reports are fresher than the queue.** A `report` with `observed` state updates that entry at once (section 4.2).

### 8.3 Staleness and the worker pre-check

The queue may be about 10 minutes old, and a mirror read is never a decision read (`discovery/mod.rs`: claim, lease, label-transition and merge reads stay live, ADR-0021 poll_gate invariant 3). So the worker keeps its existing per-item pre-check **before spawning**: re-read the item live (through the gateway, as the claim path does today) and check:

- it is still open and still in the stage the assignment names;
- it carries no hard-exclusion label, no `loom:operator`, no `loom:frozen`, no live hold;
- no open PR and no live forge lease (the `check-claim` blockers);
- for a PR step, the head is the one the queue saw, or newer and still in the step's state.

On failure the worker reports `refused` with `reason: stale` and `observed`, drops nothing locally, and asks again. The captain drops the entry and, via `observed`, corrects its view. One refusal costs one live read, which is what a lost claim costs today.

### 8.4 Cost shape

| Read | Today | Phase 2 |
|---|---|---|
| Discovery | N hosts x 1 worklist per tick | 1 worklist per ~10 min, captain only |
| Pre-check | none beyond the claim | 1 live item read per assignment |
| Claim | unchanged | unchanged |

The pre-check is new traffic, bounded by the assignment rate and far below the discovery traffic it replaces. Its exact net effect is measured in Phase 2 against the baseline (section 11).

## 9. Security

- **Tailnet only.** The captain binds to its tailnet address, never `0.0.0.0` and never a public address. A tailnet ACL (2AMLogic/2am#4976) allows the worker tag to reach the captain's port and nothing else.
- **Caller identity from Tailscale.** The captain identifies the caller by asking its local `tailscaled` who owns the connecting address: the LocalAPI `whois` for the peer's tailnet IP, which returns the node name and tags. That name is mapped to a fleet host id through the fleet config. A caller that `whois` cannot resolve, or that resolves to a node not in the fleet roster, gets `401`/`403`. The `host` field in the body is checked against it and never trusted alone.
- **No per-host credentials.** There is no token, key or secret in the protocol, in config, in argv or in a span. Following the telemetry-reader and GitHub-gateway pattern, being a permitted node on the tailnet is the credential. This differs from `forge_gateway.rs`, which keeps per-owner keys because it fronts a GitHub App installation token; the captain fronts no secret.
- **The captain holds no forge credential for writes.** It reads (mirror, then capped gateway/`gh` tiers) and assigns. All claims, labels and comments stay with the worker, under the worker's own identity. A compromised captain can mis-schedule; it cannot merge, label or comment.
- **Untrusted text.** The queue holds forge-derived titles and labels. The wire response carries repo, item number, step and priority only: no title, body or comment text. The worker never takes a step, a role or a command from queue text (`defaults/docs/untrusted-external-content.md`).
- **Replay and spoofing.** The tailnet encrypts and authenticates the transport. `request_id` dedup is for idempotence, not security. A spoofed `host` is refused by the `whois` check.
- **Loopback for development.** Loopback binding is allowed only with an explicit flag, with the caller identity set to the local host.

## 10. Telemetry

Straight to SigNoz over OTLP, with no intermediate store, following `docs/design/work-finder-step-dispatch.md` section 7 and the trace-identity policy (`.loom/docs/trace-identity.md`: every span records the Loom version and full SHA, no random trace ids). Names are provisional until Phase 1.

**Spans.**
- `loom.captain.next` (captain): host, request_id, max_assignments, returned, queue_age_secs, fit-rejections by reason, latency.
- `loom.captain.refresh` (captain): source tier (`mirror` | `gateway` | `gh`), conditional hit (`304`), repos refreshed, items in queue, **refresh cost** (latency, and forge reads spent by tier), trigger (`interval` | `change_stream`).
- `loom.dispatch.step` (worker, existing): gains `loom.dispatch.source` = `captain` | `local` and the `assignment_id`, so one query separates the two modes.

**Counters and gauges.**
- `loom.captain.assignments{host,step,outcome}` with outcome `spawned`, `refused`, `expired_unused`, `expired_no_report`.
- `loom.captain.refusals{reason}`: `stale`, `held`, `claim_lost`, `host_ineligible`, `no_capacity`.
- `loom.captain.queue_age_secs{repo}`: the age of the freshest data behind each repo's entries.
- `loom.captain.queue_items{repo,step}`.
- `loom.dispatch.fallback{host,reason}` and `loom.dispatch.mode{host}` (0 local, 1 captain): the Phase 3 exit evidence.
- `loom.forge.reads{caller=captain|worker, tier}`: the forge-read saving, the claim being sold.

**Alerts** (`defaults/observability/signoz/alerts/`, shipped with Phase 1 so each rollout is watched from its first minute):

| Rule | Fires when |
|---|---|
| `captain-queue-stale` | `loom.captain.queue_age_secs` exceeds 3x the refresh interval for any repo |
| `captain-fallback-rate` | a fleet-mode host's fallback ticks exceed a share of its ticks for 30 min |
| `captain-refusal-rate` | `stale` refusals exceed a share of assignments for 30 min (the queue is too old for its use) |
| `captain-no-assignments` | a host with open slots gets only empty answers for 30 min while the queue has items that fit it |

## 11. Rollout: Phases 1-3

Each phase has an exit criterion read from SigNoz, not from judgment. No phase begins until the previous one's criterion holds and the operator says so.

### Phase 1: The captain arbitrates claims

Workers still draw locally, but **ask the captain before claiming**. The captain answers yes (hold this item for you) or no (another host has it), from an in-memory table of outstanding holds. This is the minimal race fix, and it needs no queue: no refresh, no `whois` queue source, no new read path.

- Server: `loom-daemon fleet-dispatch serve` on the `loom-fleet-captain` unit (#12449). Client: the worker, failing open with hysteresis (#12450). Infra: tailnet ACL, captain unit, and a per-host flag on 2 workers as the A/B group (2am#4976).
- The wire contract of section 4 is fixed here, with `/v1/next` implemented in its degenerate form (`exclude` and a single candidate), so Phase 2 changes the captain's behaviour and not the protocol.
- **Exit criterion.** Over at least 7 days, the A/B group's `claim_lost` share of step draws is a small fraction of the control group's (target: under 5% against the 37% baseline), the group's slot occupancy is no lower, and `loom.dispatch.fallback` is under 1% of ticks outside planned captain restarts.

### Phase 2: The captain assigns from the fleet queue

Workers call `next()`; the local draw is the fallback only. The queue (section 8) is fed by #12304's mirror read. This is where the GitHub-read savings arrive.

- **Prerequisite.** #12304's single mirror read is in production fleet-wide.
- **Exit criterion.** For the fleet-mode group over at least 7 days: forge reads per tick (captain plus workers) are a fraction of the control group's, occupancy at cap is at least the control's, `stale` refusals are under 10% of assignments, and the fallback rate holds the Phase 1 bound. Widen the group stepwise (2 hosts, then half, then all) with the same check at each step.

### Phase 3: Retire the per-host gather and the claim machinery

Remove the per-host gather and the claim and peer-claim machinery once SigNoz shows the fallback is rare. **Gated on data, not on a date:** `loom.dispatch.fallback` stays under a stated bound (default 0.5% of ticks) across all hosts for a full release cycle, with at least one planned and one unplanned captain restart inside that window.

- **The local draw is not removed outright.** Fail-open (section 7) needs a local path. Phase 3 retires the *redundant* pieces: the per-host fleet-wide gather in favour of the minimal per-repo read the fallback needs, and the peer-claim channel (2am#4566). What remains is the smallest fallback that still satisfies section 7.4.
- **Rollback.** Each phase is revertable by the per-host flag (Phase 1-2) or by reverting the merge (Phase 3), and Phase 3 lands only after the flag has been unused in production for the window above.

## 12. Edge cases

- **Captain restart mid-assignment.** Section 6.4. Outstanding assignments are forgotten. The forge leases of started work are untouched, so started work carries on, and not-yet-started assignments lapse and return to the queue. A worker that calls `/v1/report` after the restart with an unknown `assignment_id` gets `200` with `ignored: true`; its forge claim stands.
- **A worker that dies holding an assignment.** Before `spawned`: the assignment TTL expires and the item is re-queued. After `spawned`: the forge lease stops being renewed, goes stale after `LOOM_LEASE_TTL_MINUTES`, and the existing reclamation (#6286) returns the item to `loom:issue`, from where the next refresh queues it again. The captain adds no timer of its own here.
- **A stale queue entry whose item was already closed or moved.** The worker's pre-check (section 8.3) refuses it with `observed`. The captain drops it. The cost is one live read; no claim is attempted and no label touched.
- **Two captains.** `fleet.captain` names exactly one host (assigned, not elected), and `fleet_captain.rs` fails closed on a mismatch or on none declared. A second captain unit cannot arm. If one did, the forge still decides every claim (section 6.1), and the symptom would be duplicate assignments showing up as `claim_lost`.
- **Captain host down for hours.** Every worker is in fallback. Dispatch is today's behaviour, including its forge load. Re-assigning `fleet.captain` to another host (a config change, not an election) restores the service. A lease/failover for the captain is #8902 and stays out of scope here.
- **Mirror down.** The captain falls to the capped gateway and `gh` tiers (section 8.1). The queue is staler and thinner; assignments still work and the pre-check protects against the staleness.
- **Item pinned to a host that never asks.** It waits in the queue, ages, and raises `captain-no-assignments` or the existing stalled alert. It is never handed to an ineligible host.
- **Thundering herd after an outage.** Workers leave fallback only after the dwell time (section 7.3), and `retry_after_secs` is jittered per host.

## 14. Alternatives considered

- **Matrix peer-claim channel (2am#4566).** Hosts announce claims to a room so peers skip claimed items. Rejected as the fix: it only narrows the race (announcements lag the draw), adds a transport with its own failure mode, and does nothing for forge-read volume. The operator made it low priority.
- **Per-host credentials for the captain API.** Rejected: tailnet identity already says which host is calling, and a key per host is a rotation burden with no added guarantee.
- **Captain holds the forge claim for the worker.** Rejected: it would make the captain's table authoritative, make a captain fault stop dispatch, and put a write credential on the captain. The forge lease stays the record (section 6.1).
- **Elect the captain.** Rejected: assigned, not elected, as `fleet_captain.rs` says. Failover is #8902.
- **Raise the pass limits.** Tried as #12448 and reverted in #12457. It treats the symptom and leaves the collisions.
- **Server-sent assignments (push).** Rejected for Phase 1-2: a push needs the captain to know each host's live capacity continuously. Pull keeps the capacity count where it is true. Revisit if the `next` latency shows up as idle slots.
- **Per-host sharding of the item space** (as `autonomous.roleRunner.shardCount` does for roles). Removes the race without a server, but fixes each host to a slice, so a host with a slow or ineligible slice idles while others are loaded, and it cannot honour host pins or per-host tools without a lookup. A central assigner subsumes it.
