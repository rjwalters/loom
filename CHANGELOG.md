## [Unreleased]

### Added

- **The forge stage-dwell gauges can be produced once per fleet, by the captain, with dispatchers standing down only while the captain's data is fresh** (W12 of the forge API reduction plan, part 1). `loom.forge.stage_dwell` / `loom.forge.stage_items` list the same stage labels of the same repos on every host that manages them, and read the same per-item events, so N hosts spent N times the reader budget on N copies of one fact. New `observability::captain_gauges`: on the declared `fleet.captain` with `fleet.captainGauges.enabled`, the singleton job `stage-dwell` is armed (`host.health.armed_singleton_jobs`) and the captain publishes a `captain-gauges/v1` heartbeat (`captain/gauges.json`) to the fleet store beside its ETA fit, on `fleet.captainGauges.ref` (default the `fleet.etaFitRef` branch; the store's reviewed branch and `main` are refused, as for the fit), every `fleet.captainGauges.publishIntervalSecs` (600). The heartbeat carries, per job, the `as_of` of the captain's last finished pass and the repos it covered. A dispatcher with `fleet.captainGauges.standDown` (env `LOOM_CAPTAIN_GAUGES_STAND_DOWN` overrides it) reads it once per collector pass with `If-None-Match` and skips a repo only when the heartbeat names the declared captain and its `as_of` is within `fleet.captainGauges.maxAgeSecs` (1800: two publish intervals plus two collector passes). It drops its sampler state for that repo, so taking the repo back starts from a baseline instead of replaying the captain's transitions. A read failure keeps the last heartbeat ageing; a missing or malformed one is absent; no `fleet.repo` means no heartbeat. Two new gauges make a captain outage visible: `loom.captain.gauge_age_seconds{task}` (captain: its own production age; dispatcher: the published `as_of` age) and `loom.captain.gauge_fallback{task}` (dispatchers: `1` while producing locally because the captain is stale). Both switches default off and older daemons ignore the keys, so an unconfigured or mixed fleet keeps today's behaviour; rollout is deploy everywhere, enable on the captain, then enable `standDown` once the captain's age gauge is steady. Per-host gauges and dispatch gates (`role_queue_gate`, `role_demand`) are untouched. ETA queue friction needs no change: it already runs only on the ETA authority (#10498), which defaults to the captain. `write_scope`'s fleet-store scope now names each caller's captain gate, and the heartbeat writer is reviewed into it. Star-liveness facts and escalation and the `loom:blocked` snapshot rows are the second part.

- **One table says which labels travel from a parent issue to its children** (#10012 §6, part). `star_liveness::propagation_rules` lists the three rules: the star goes to issues and PRs and is removed with the parent's star; `external` goes to issues and is removed with the parent's label; `tier:*` is a default for an untiered child and is never overwritten or removed. Everything else never propagates (holds, claims, lifecycle, PR lanes, proposals, `loom:epic-phase`, `loom:heavy`, `points:*`, `loom:urgent`, the #10307 level labels). A pure `plan()` computes the adds and removals for one child. It removes only a copy that propagation itself wrote, and never after an incomplete walk. A unit test fails when a `defaults/labels.json` label is in neither the table nor the never-propagate list. Nothing writes labels yet; the materialization pass is the next slice.

- **Reader choice goes through one routing step that can split a hot repo across the reader pool per URL and spill off a home reader that is running dry** (W4-B of the forge API reduction plan). Reader selection used to be one `hash(owner/repo) mod N` per repo in three separate walks, so a hot repo drained one reader's bucket while the other idled. `forge_identity::route_read(&RouteRequest { owner_repo, host, resource, affinity_key, class }, now)` replaces those walks and returns `NoPool`, `Reader { dir, app_id, placement: Home | Split | Spill }` or `Exhausted { until }`; `read_credential` / `read_credential_for` are wrappers with no affinity key (home placement, `Exhausted` mapped to the writer). Home placement is unchanged (`assignment_index`, same golden table); a reader entry may carry `owners: [..]`, and `N` then counts only readers serving the repo's owner. A repo in `forge.readPool.routing.splitRepos` (default `[]`) starts each request at `SHA-256("loom-read-pool/split/v1:" + owner/repo + "|" + affinity key)` mod N, where the affinity key is the argv without `-H`, `--jq`, `--template`, `--include`, `--paginate`, `--hostname` and `--cache` (or a conditional read's URL), so a URL always lands on one reader: GitHub ETags are credential-specific, and a moved URL loses its 304. A per-`(repo, resource, home)` spill latch engages partial at a home projection of `spillProjectedPct` (70; moves the fixed half whose spill hash is odd) and full at `spillFullPct` (90) or while home is withdrawn, targets the next reader projected below `targetMaxPct` (60, or unknown; else stays home) and pins that target until release unless it is withdrawn, stale or reaches `spillFullPct` (so a target crossing 60% never bounces URLs, each move costing a 200), never engages on an unknown reading, and holds until the home bucket's reset (the later of the reset and a live withdrawal's end, capped at 3660 s; 3600 s when no reset is known). Each transition emits a `forge.reader.spill` span and `status` lists engaged latches. `fetch_conditional` and the `gh` choke point route with their affinity key; the ETag cache key is unchanged. `LOOM_READ_POOL_SPILL=0` keeps every read home, `LOOM_READ_POOL_SPLIT=0` disables the split, and `LOOM_READ_ROUTING=legacy` restores the pre-W4 walk. In v2 an egress policy that gives the gateway the GitHub credential now also keeps `read_credential` off the pool. With no `splitRepos` and no reading at 70% or more the reader chosen is the same as before.

- **A rate-limited reader App is withdrawn only from the `(owner, resource)` bucket that refused it, until that bucket's real reset** (W4-A of the forge API reduction plan). GitHub meters each App installation per owner and per resource, but a rate limit anywhere used to withdraw the reader App-wide for a flat 300 s, so one owner's dry `core` pool took the reader off every other owner and pushed all of them onto the writer. `forge_identity::Failure` now splits into `RateLimited { resource, reset, secondary, retry_after }`, `Credential` and `Coverage`, classified from the failed response's own `x-ratelimit-*`/`Retry-After` headers where the call printed them. A primary limit withdraws `(app, owner, resource)` until the refusal's `x-ratelimit-reset`, else the reading of a free on-demand `gh api rate_limit` probe (throttled to one per App and owner per minute, run under that reader's directory with token env stripped, booked to `other`), else 300 s, clamped to [30 s, 3660 s]; it also books the bucket exhausted in the bucket book. A secondary limit withdraws that owner's `all` for `Retry-After` or 60 s, never the hourly reset; bad credentials withdraw `all` for 300 s; coverage is unchanged; only mint and key failures stay App-wide. Reader choice (`reader_for_at`, `read_credential_for`) skips a reader withdrawn for the call's owner and resource; the choke point, `fetch_conditional`, `ci_telemetry` and both ETA fetchers pass their parsed headers. Each withdrawal emits a `forge.reader.withdrawn` span and `loom-daemon status` lists the live scoped ones. The reader-then-writer retry is unchanged. `LOOM_READ_ROUTING=legacy` restores the previous classifier, App-wide withdrawal and TTLs exactly.

- **Forge-call ledger rows now name the billed GitHub bucket, and a per-credential bucket book plus `loom.forge.calls` make every App installation's pool visible** (W1 of the forge API reduction plan). GitHub bills each App installation separately per resource, but the ledger said only *what* spent budget, so a draining pool could not be traced to a credential, and untargeted calls often carried no repo. Each facade row now records its credential (`ca` account `app-<id>`/`app-unknown`/`env-token`/`ambient`, `co` installation owner, `tk` kind), classified from the effective `GH_CONFIG_DIR` path shape alone and never a path or token. It also records the billed resource (`rr`, from `x-ratelimit-resource`, else the argv's pool), a page count (`pg` from `--paginate --include` status blocks, 2 for `run download`, `pu` when unknown), and where its repo came from (`ro`). An untargeted call in a checkout now takes its repo from the memoised local `origin` remote, which is never a forge call, and `rd` flags a remote that disagrees with what `gh` itself would resolve (`facade.cwd_route.disagree`). `x-ratelimit-limit` is parsed too. The new `forge_bucket_book` keeps the newest reading per `(account, owner, resource)` from response headers and from one free `gh api rate_limit` probe per published credential directory after each reader-refresh pass. Probes run under that directory with token env stripped, booked to the free `other` pool. Readings are exported as `github.ratelimit.{remaining,used,reset}` with a new `owner` label; the account-only points are unchanged. `loom.forge.calls` (delta counter; caller, op, role, account, cred_owner, target_owner, resource, outcome) is flushed on the rate-limit tick and accumulates only with an ops sink. `loom-daemon forge calls [--since 1h] [--by bucket|caller|role|repo]` and a compact `status` block show charged/304/limited per bucket beside the book's readings, from local files only. No call is routed differently and every new sink key is optional, so older lines and readers are unaffected.
- **The work finder's operator starred-at survives a daemon restart** — every restart or roll used to re-read the REST timeline of every starred issue in every workspace at once, a burst of `work_finder.starred_at` calls on each roll. Known values now persist in a per-workspace `starred-<sha16(cwd|repo)>.json` beside the listing cache (atomic, private dir, 7-day GC). The store never changes what a running daemon decides: it is read only on an in-process miss, after a loom-ui intent's `requested_at` (which always wins); a value is reused only with the same level-label set, seen within 30 minutes, and confirmed under a listed `updated_at` no older than the issue's current one (free on the ETag-cached listing row; a missing one reads), so an unstar and re-star made on the forge while the daemon was down is read rather than masked — and the same check now re-reads a known value in process once the issue is updated, closing the old "flipped between two ticks" staleness; unknowns are never written (the 10-minute retry still applies); and each in-process eviction is mirrored, so an unstar and re-star still reads the new time. The timeline read is now typed (`GhTarget::Repo`) with an explicit `repos/<slug>/…` URL whenever the slug is known (explicit repo, else `LOOM_REPO`, which is what the placeholder resolved to). A `starred_at_cache` tally (`mem_hit`, `disk_hit`, `intent_hit`, `read_known`, `read_none`, `read_err`) on the published tick summary (and so in `status`) shows how much timeline volume remains and how much of it is unknown-value retries. Kill switch: `LOOM_STARRED_AT_PERSIST=0`.

- **Operator priority levels: ⭐⭐ `loom:operator-high-priority` above the star** (#10307, part 1). The star (`loom:operator-priority`) had filled up (63 of 277 open loom-ui issues), so it no longer said "this one, now". Levels are data: one table (`loom-daemon/src/operator_levels.rs`) maps level → operator label, inherited label and cap; level 3 (⭐⭐⭐) will be one more row. Level 2 adds two labels (`labels.yml`): `loom:operator-high-priority` (human-only, like the star; capped at 5 by loom-ui) and `loom:high-priority-inherited` (daemon-written; part 2 writes it on every open blocker). Levels nest, so level ≥ 2 counts as starred everywhere, and every starred-first pass now drains by effective level, highest first: the work finder (a new leading `operator_priority_level` dispatch key, one listing per level label, starred-at re-read on a level change), `loom-daemon pr-queue` (Judge/Doctor/Champion; rows gain `operatorPriorityLevel`), Curator Priority 0, Builder's starred-first query, and Champion's epic queue and hold digest (⭐⭐). The loom-ui intent relay accepts a level-2 intent (`label: "loom:operator-high-priority"`) and applies or removes exactly that label, never the star; an inherited label is never accepted from an intent. The audit marker gains ` label=<label>` (no `label=` still means the star). No level label is a hold: `pr_latency`'s `loom:operator-` prefix match excludes them by name.

- **Sustained OTLP export failures now escalate into a loud, actionable operator warning** (#9950) — every failed flush already logged a per-flush diagnostic (`export diagnostic, N envelope(s) remain queued`), but a dead sink produces a stream of near-identical WARNs whose *number* carries the only signal, and `status`/`health` surface the truth only when someone thinks to run them. During a real outage (2026-10-01: an edge host's SSH tunnel to the telemetry store died at a store cutover — 2AMLogic/2am#1878), every record the daemon produced was trapped locally for ~15h and the operator learned of it from a remote report, not from the failing machine. Now, after `ESCALATE_AFTER_FAILURES` = 12 consecutive failed flushes (~1h of continuous dead sink at the 5-min backoff ceiling), `try_flush` logs one escalated WARN that says plainly telemetry is **not reaching** the configured endpoint, for how long ("last success … ago" or "never had a successful export"), how many envelopes are accumulating, and **what to do**: check this host's OTel egress (edge collector / tunnel / ingest key) and the endpoint itself, run `loom-daemon health` for the verdict and `loom-daemon status` for the live line. The escalation re-fires every `ESCALATE_EVERY_FAILURES` = 24 further consecutive failures (~2h) — a heartbeat for a multi-hour outage, never per-flush noise — and `record_success` resets the clock, so a post-recovery regression starts a fresh streak. The `Failing` status line gains the same one-clause fix pointer (`— fix: check this host's OTel egress …; loom-daemon health has the verdict`) so an operator reading it cold needs no second command to know where to go. The cadence decision is a pure function (`should_escalate`), unit-tested, and the escalated line's severity and content are asserted through the crate's `capture_logs` helper (thread + current-thread runtime, since the capture is thread-local and a runtime cannot be entered from within one). Deliberately unchanged: export/retry/backoff semantics, queue durability, and the health section's anomaly-only rule (#4830) — this is purely an escalation of visibility; the `Misconfigured` state (#5337) already names the offending path and errno and does not need the treatment.

- **A `daemon_status` MCP tool makes the daemon's telemetry-export state an agent surface — with a relay directive** (#9950) — the daemon already computes `ObservabilityExportStatus` (state, endpoint, consecutive failures, backlog) and renders it on the human CLI (`loom-daemon status`), but `DaemonStatusReport` flowed nowhere an agent reads: mcp-loom exposed logs/ui/terminals/sweeps and nothing status-shaped. During the 2026-10-01 store-tunnel outage (2AMLogic/2am#1878, ~15h of telemetry trapped on the operator's laptop) the agent working on that host could not have seen the daemon's verdict without shelling out to the CLI, and nothing told it to relay what it found. The new `daemon_status` tool performs one bounded `Request::DaemonStatus` round trip and renders the headline fields (build, in-flight sweeps) plus the `Observability: …` line — and, when the state is a problem (`failing`, `never_exported`, `misconfigured`, or the host-id mismatch), an explicit **`⚠️ TELEMETRY WARNING — RELAY TO THE USER`** block naming what is broken and the fix path ("check this host's OTel egress (edge collector / tunnel / ingest key) and the endpoint itself; `loom-daemon health` has the verdict"). The tool's description states the expectation in agent-readable terms: a relay directive is a to-do for the calling agent, not metadata. Healthy/disabled/starting states stay quiet — relay pressure applies to actual findings, never to a deliberate off. A dead daemon socket is relayed too, as its own finding ("sweeps and role ticks are not running…"). Renderers are pure functions (`describeObservability`, `relayDirective`, `renderDaemonStatus`) over the daemon's `{type, payload}` wire shape, unit-tested against wire fixtures (11 assertions: state wording, first-hop scope, relay presence/absence per state, the unknown-payload and dead-socket paths).

### Fixed

- **CI telemetry's page 2+ reads and artifact downloads now run on the repo's reader App, not the writer.** The poller already sent `repos/<owner>/<repo>/…` reads to that repo's reader, but GitHub's `Link: rel="next"` target for page 2+ of a run, job or artifact listing is `repositories/<id>/…`, which names no repo: those pages fell through to the writer credential and were accounted under no repo (and, by route, as `unknown`). `GithubApi` gains a default `get_in(repo, path, etag)` (it ignores `repo`, so every test fake is unchanged); `GhCliApi` overrides it to pick the reader and the accounting `rp` from the named repo, and `poll::paginate` passes page 1's repo for every page. `ci_operation` maps the `repositories/<id>/actions/runs[/<id>/jobs|/artifacts]` spellings to the same inventoried operations as page 1. `gh run download` (suite/test-timing artifacts) now goes through the shared `reader_then_writer` retry: reader first (its own `GH_CONFIG_DIR`, token env stripped, role `reader`); a rate limit or bad credential withdraws the reader App-wide and retries on the writer; a 403/404 retries on the writer and withdraws the reader for that repo only if the writer succeeds; a 5xx or timeout is not retried. With no reader configured the download invocation is byte-for-byte the previous one. Owner discovery (`orgs/…/repos`, `users/…/repos`) and the closing-issue GraphQL lookup stay on the writer. Tests: `ci_telemetry/tests/reader_routing.rs` (9).

- **`landed-size.sql` and `story-points-calibration-queries.sql` now run on Cloudflare D1, and CI refuses any observability SQL that D1 would refuse for compound-SELECT size** (#10066). D1 caps a compound SELECT at 5 terms (`too many terms in compound SELECT`). `landed-size.sql` had two 6-term `UNION ALL` lists (`measured_point_values` and the `model_token_factors` CTE), and the calibration file's `rubric_classes` view had one. Bundled SQLite's default limit is 500, so every execution test passed while production refused the file atomically and LSI could not go live. All three lists are now multi-row `VALUES`, which is exempt from the limit, with byte-identical column names and values (the `v1-2026-10-02` params and the measured ratios are unchanged). `fit-landed-size.mjs` now emits `model_token_factors` in the same `VALUES` form, so a refit with six or more models cannot reintroduce the bug. Two enforcement layers: (1) a new `loom-daemon/tests/support/d1_sqlite.rs` opens the execution tests' connections (`landed_size_sqlite`, `issue_effort_sqlite`, `story_points_calibration`) with `SQLITE_LIMIT_COMPOUND_SELECT = 5` (rusqlite's `limits` feature is enabled for this); (2) `loom-daemon/tests/sql_compound_select_limit.rs` is a static, per-chain (paren-depth-aware, comment- and string-skipping) scan of every `.sql` under `defaults/observability/`, which also covers files no test executes. Its fixtures pin a 6-term refusal, the CAL3 shape (a 5-term chain beside a recursive CTE chain in one statement, which D1 accepts), and the `VALUES` exemption, and each is cross-checked against SQLite with the limit applied. The `rubric_classes` contract regex now parses `VALUES` rows. Running `landed-size.sql` against D1 remains an operator step after merge.

- **`accounts session start` now mounts the daemon's GitHub App token dirs even when `LOOM_WORKSPACE` is unset** (#10103). A host-mode session container finds the token dirs it mounts read-only (`.loom/gh-config`, `.loom/gh-config-by-owner`) by looking under a list of candidate owners. That list used to hold only the `--mount-workspace` path and `$LOOM_WORKSPACE`. So when an operator ran `cd ~/GitHub/loom && loom-daemon accounts session start agent-3 --mount-workspace ~/GitHub` by hand, nothing was found: `~/GitHub` has no token dir and `LOOM_WORKSPACE` wasn't set. Nothing was mounted, posture reported `gh=skip`, and Codex roles in that session couldn't authenticate `gh`. The accounts registry's own workspace is now an owner too. That is the `--workspace` daemon root whose `.loom/accounts.json` `session start` updates, and it defaults to the current checkout. The new `session_lifecycle::gh_credential_owners` builds the list `[mount workspace, registry workspace, $LOOM_WORKSPACE]` without duplicates, and `ContainerRunner::create` receives the daemon root. What may be mounted is unchanged: only those two daemon-shaped dirs, never an arbitrary `GH_CONFIG_DIR`. The posture hint now points at the daemon root instead of only `LOOM_WORKSPACE`. Existing containers keep their mounts until they are recreated (`accounts session stop` / `start`). Tests: `session_lifecycle_owner_tests.rs` (3).
- **Codex session seats no longer need the interactive hook-trust prompt: Loom passes `--dangerously-bypass-hook-trust` only for a registration it has proven is sealed** (#10102). Accepting Codex's hook-trust prompt was the last manual blocker for the Codex lane. It had to be done once per profile per host (about 26 seats), and a session container couldn't save the decision because `config.toml` is a read-only bind. Codex 0.160's waiver is "intended only for automation that already vets hook sources", so Loom now does that vetting itself. The new `tokens_pool::codex_hooks::seal` checks every non-managed hook source the flag could enable in Codex 0.160's discovery:
  - **Location.** The launch runs inside a hardened host-mode session container (posture `host`), never on bare metal.
  - **`hooks.json`.** It is exactly Loom's #10008 entry: one `PreToolUse` group, matcher `*`, one `command` handler with timeout 30–600, no other key, and no duplicate keys. The receipt pins the command.
  - **`config.toml`.** It adds no `[hooks]` events, doesn't set `enabled = false` on Loom's key or `features.hooks = false`, has no `project_root_markers`, and no `profiles.*` touching hooks, features or plugins.
  - **Project layers.** There is no `.codex/hooks.json`, and no `.codex/config.toml` touching those keys, from the cwd to the git root or in a worktree's main checkout.
  - **Session flags.** The argv has no `-c` on those keys, no `--enable`/`--disable`/`--profile`, no `-C`/`--cd`/`--worktree`, and no caller-supplied waiver (`spawn-codex.sh` exits 78 on one).
  - **Plugins.** These can't be vetted, so the launch also passes `-c features.plugins=false`.
  - **Byte identity.** The container's copies of the three profile controls hash to the exact bytes vetted (`docker exec … sha256sum`).

  Every clause allows only what Loom writes, so it fails closed. Anything else refuses the seal, and readiness falls back to recorded trust exactly as before: a hook-required role exits 78 and the daemon routes to the next runtime, while a read-only role runs with `trust-bypass=never`. Sealing is opt-in (`codex-hooks verify --allow-sealed`, with new `--cwd`/`--container`/`--docker` and the Codex argv after `--`). A caller that wouldn't pass the waiver never sees a sealed seat as ready, and `spawn-codex.sh` falls back to recorded trust if the daemon predates the flag. The verdict gains `bypassHookTrust`, `containerVerified` and `sealReason`, plus `trustSignal: "sealed-registration"`. The audit line reads `trust-bypass=<never|sealed>`. The #10035 guard gate (`runtime_preference::codex_guard`) counts a sealed session seat as guard-ready. **#4495** forbade the flag because waiving trust would let a hook nobody reviewed run. The vetting is that review, and three facts #4495 lacked keep it true for the whole session: the container is the boundary (#10014), the profile controls are read-only binds, and their bytes are proven. Private-clone sessions and bare-metal profiles never use the waiver. `provision-codex-hooks.sh verify` now hands its arguments straight to the daemon (net shell shrink). Real-container evidence on robb-studio (shipped session image, Codex 0.160.0, session flags, read-only controls):
  - A sealed, untrusted judge seat blocks `git push --force origin HEAD:main` through Loom's hook, and the remote doesn't move.
  - The same container without the waiver lets the push land.
  - An extra hook, a changed matcher, or a project `.codex/hooks.json` refuses the waiver (judge exits 78).

  Tests: `codex_hooks_seal_tests.rs` (11), `codex_guard_tests.rs` (+1), and the new `test-spawn-codex-sealed.sh` (38; Native Port Suites). The static waiver tests in `test-spawn-codex.sh` and `test-provision-codex-hooks.sh` now require the flag on exactly one line, gated on the sealed verdict. Operator rollout, per host: `provision-codex-hooks.sh install --all-profiles`, restart each adopted host-mode session, then `verify --all-profiles --allow-sealed --json` (`guardrail-parity-codex.md` § "Sealed registration").

- **Codex role sessions in `loom-codex-session-*` containers now actually run commands. Codex's sandbox is off there and the hardened container is the boundary** (#9979). Codex's bubblewrap sandbox can't create a user namespace under Docker's default seccomp, nor under Ubuntu's AppArmor userns restriction. Every role tick failed its first shell command with `bwrap: No permissions to create a new namespace` and exited 0 having done nothing. Under the operator's 2026-10-03 ruling, `spawn-codex.sh` now runs `-s danger-full-access` in a session container, but only in one created hardened. `accounts session start` now creates host-mode containers with `--cap-drop ALL` and `no-new-privileges`. It mounts only the registered repositories, not the whole checkout parent, plus the daemon's App-token dir read-only. It no longer mounts the Claude token pool or the operator's `~/.config/gh`. It refuses `/`, the home directory and its ancestors, and anything overlapping a `firewall: true` repository in the cached fleet roster. Containers created before this release exit 78 until they are recreated. So does any container whose actual settings, as checked by the new `loom-daemon session-exec posture`, (privileged, host namespaces, added caps, `unconfined`, docker.sock, missing cap-drop or `no-new-privileges`) don't match its posture label. `GH_CONFIG_DIR` is forwarded so `gh` works in the container. `docker/session/test-image.sh` now proves that a real Codex tool call executes under the session posture. **The profile's hook-control files are frozen too.** A host-mode container now binds `hooks.json`, `config.toml` and `loom-codex-hooks.json` read-only over their own paths, as private-clone sessions do. `session start` first creates any missing one as an inert placeholder. Without this, a sandbox-off session could edit its own profile so that the next session read as guard-ready while Codex skipped Loom's hook. One way: change the hook's `matcher`, which keeps the pinned command but voids Codex's whole-group trust hash. `session-exec posture` exits 78 with `profile-control-writable(<file>)` when a bind is missing or writable. In host mode it also exits 78 when the container's copy of a file differs from the host's (`docker exec … sha256sum`; `spawn-codex.sh` passes `--codex-home`). A file bind does not follow a host-side replace, so after provisioning or accepting trust the container would see a stale file, or none at all on Docker Desktop, while the host verified ready. Restart the session after either step. Tested against Codex 0.160.0: `codex exec` and `codex login` run normally with the files read-only. The interactive TUI can't save a folder-trust or hook-trust decision there, so for now take those in a throwaway container with the profile writable (`guardrail-parity-codex.md`). Tests: `posture_tests.rs` (every control × RW/volume/elsewhere/missing under both labels, drift, parsing), `session_lifecycle_tests.rs` (binds, placeholders), `test-spawn-codex-session-exec.sh` (per-file writable/unbound/stale), and `test-image.sh` §13 (write/unlink/rename/symlink refused, controls byte-identical after a real Codex turn).

- **Champion and Judge on Codex now require Loom's guard hook, and fall back to the next runtime instead of failing when it is missing** (#9390). Champion merges, and Judge issues the verdict Champion merges on. That is the forge authority `guard-loom-workflow.sh` and `guard-destructive.sh` police. Yet `spawn-codex.sh` treated both as read-only roles and launched them with only a warning when the managed hook was not ready, which is why champion was pinned to Claude on robb-studio. Three layers now:

- **`tap_usage` now reads Pi's real `message_end` shape, so a Pi launch is measured instead of reading as unmeasured tap spend** (#8934) — #8556's fixture guessed `{"type":"message_end","usage":{"input_tokens":…}}` with the counters on the event itself; Pi 0.85.1 (`@earendil-works/pi-coding-agent`, the pinned `PI_VERSION`) actually nests them on the **message** — `{"type":"message_end","message":{"role":"assistant","usage":{…}}}` — which `read_event_usage` never searched, so a real Pi run reported zero usage events and every Pi launch's tap accounting (`tap_usage` on `sweep-outcomes.jsonl`, `config.tap_*` on `sweep.outcome`) read as unmeasured — the exact metered-backstop spend #8556 and ADR-0020 exist to see. `message.usage` is now searched **in addition to** the flat `tokens`/`usage`/event-root scopes OpenCode uses, never instead of them, and two of Pi's semantics (`pi_usage`'s "Schema provenance" section is the authority for both, read off the shipped `@earendil-works/pi-coding-agent` / `pi-ai` packages) are honoured with it: `reasoning` is a **subset** of `output` for Pi (not an addition, as OpenCode's is), so a reasoning count read out of `message.usage` is dropped rather than double-counted inside `output` — `TapUsage::total_tokens` sums every counter it is given and a `TapUsage` carries no harness tag to key the difference on; and `cost` is an **object**, not a bare number, so the estimate is read from its rollup `cost.total`. One deliberate divergence from `pi_usage`: a `toolResult` message's nested `usage` (LLM work done inside a tool) **is** counted here, because this module keys by the *tap* the enclosing `# LOOM_LAUNCH` record names rather than by model, so there is no model to guess and dropping it would be a knowable undercount — `pi_usage` excludes the same reading for the opposite reason, since it keys by model and such a reading names none. `entry_appended`, which re-emits every persisted session entry (assistant messages included), is excluded for the same reason `agent_end` already was: `USAGE_EVENT_TYPES` is an allowlist, so any further Pi repeat event is excluded by construction rather than by a rule to maintain.

- **`observability_export`'s `healthy` state now names the hop it verifies, instead of reading as end-to-end delivery** (#9015) — the daemon has only ever measured whether the *configured* `observability.endpoint` acked the batch it POSTed; nothing past that endpoint is observable from here. In the harness-ops deployment that endpoint is a local otel-edge collector forwarding to SigNoz, and from 2026-09-24 to 2026-09-26 its egress tunnel was never installed: the daemon reported `state: healthy`, `rejected: 0`, `dropped: 0` for 30h+ while the collector logged ~6,755 `Exporting failed. Dropping data.` lines and SigNoz held no continuous `service.name=loom` data — found only by querying ClickHouse directly. Every `ObservabilityExportStatus` now carries a derived, never-configured `scope` (`"first_hop"`, the only value this daemon has ever measured — an unrecognized value from a newer daemon reads back as `unrecognized` rather than failing the parse) and `endpoint_loopback` (`true` when `endpoint` resolves to this machine — `127.0.0.0/8`, `::1`, `localhost` or a DNS child of it — i.e. almost always a forwarding edge collector, via a new `observability::endpoint_policy::is_loopback_endpoint`). `loom-daemon status`'s human line now reads `Observability: OK (first hop only)`, and adds `(LOCAL collector: delivery to the backend PAST this hop is not verified here — check the backend read-back, or the collector's own otelcol_exporter_send_failed_* counters)` whenever the endpoint is a loopback address; `status --json`'s `.observability_export` / `.observability_exports.<name>` and `health --json`'s `observability` section detail carry the same two fields. Both are re-derived from `endpoint` at every point a status cell is built or snapshotted (`ObservabilityExportStatus::refresh_endpoint_scope`), and the renderers additionally re-derive the loopback flag live (`endpoint_is_loopback`) rather than trust the wire value, so a payload from a pre-#9015 daemon binary — the ones actually running today — still renders the caveat instead of silently omitting it. `defaults/docs/observability.md` and `daemon-reference.md` now document the first-hop limitation explicitly and recommend an external end-to-end check for edge deployments (a backend read-back canary modelled on harness-ops `signozliveness`, or scraping the collector's own `otelcol_exporter_send_failed_*` / queue-size metrics on its `:8888` telemetry endpoint); an in-daemon downstream probe surfaced as a distinct `degraded_downstream` state is out of scope for this change and tracked separately.

- **A drain-and-restart roll whose wait condition is unsatisfiable is now abandoned instead of re-armed indefinitely** (#8998) — #6007 made a refused drain deadline *retain* the roll intent (dispatch stays paused, the restart re-arms itself at quiescence) and bounded that retention with a total paused-dispatch budget so a wedged sweep could not starve the host of work forever. Both halves are correct, and neither bounds the thing that actually livelocked: the **sequence** of drains. `auto_update` arms a roll → the deadline expires with sweeps in flight → the fail-safe correctly refuses to cancel them → the budget is eventually spent and the roll is abandoned → a new release lands (the fleet cuts one roughly every 30 minutes) and step one happens again; #8514's supersede restarts the same budget mid-pause. Every step is individually right and the aggregate never terminates. On 2026-09-25 two fleet dispatchers spent **21 hours** in that cycle — 72 and 65 consecutive `"a drain-and-restart roll is already armed (dispatch paused, waiting for in-flight sweeps to reach zero) — skipping this tick"` ticks, spanning 04:45Z → 02:01Z — and never once rolled. The blocker on `loom-worker-1` was a genuinely-working 9h32m analog-simulation sweep (`sky130-sar-adc#431`, ngspice corner runs, writing results as recently as 9 minutes before the survey), so on a host doing analog work "wait for in-flight to reach zero" is structurally unachievable against a 30-minute drain deadline, not a symptom of a stuck sweep. The cost was not only version skew: `draining: true` suppresses **role spawns** as well as sweep dispatch, so `robb-studio` produced zero role ticks for 4h20m purely because of this, starving the curator/champion stages. The loop now counts drain deadline expiries **across roll lifetimes** — `DrainDescriptor::refusals` restarts at `0` on every fresh drain, which is precisely why counting only the live roll's refusals could never conclude anything — and tracks the lowest in-flight count observed at any of them. Once `autonomous.autoUpdate.rollStallDeadlines` (`LOOM_AUTO_UPDATE_ROLL_STALL_DEADLINES`, default `3`) deadlines have expired with that floor never improving, the roll is **abandoned**: discarded through the same `--abort-drain` primitive #8514's supersede already uses, so the pause flag clears, the generation bumps (the live supervisor stands down without exiting the process), #6007's pending bookkeeping is fully reset, and normal dispatch — including role spawns — resumes rather than leaving `draining: true` latched. No new roll is armed until in-flight is observed at **zero**, at which point the suppression clears and the roll lands on its own with no operator action. Be precise about that clearing condition rather than calling it self-clearing: it is an auto-update tick *sampling* `in_flight == 0` on the `intervalSecs` cadence (default 900s) **with dispatch running**, which is strictly harder than the drain's own quiescence watch (continuous, and observing a paused dispatcher where in-flight can only fall) — on a busy cap-12 dispatcher a 900s sample can miss every lull, so the host can stay un-updated for an unbounded time with no time-based retry. The trade is therefore *unbounded paused dispatch* for *unbounded staleness on a permanently-busy host*, which is the better of the two but is not "it fixes itself shortly"; a bounded cooldown retry is tracked as #9010. A decrease that still leaves work running (7 → 2 while the 9-hour sweep continues) deliberately does *not* clear it, because re-arming there buys another full budget with the same outcome, which is the cycling being stopped. **The #6007 fail-safe is untouched — no sweep is ever cancelled**, and the pre-update binary keeps running; what changes is that a silent indefinite livelock becomes one loud, actionable state, logged at WARN, published as `auto_update_note`, recorded as `drain_note`, and emitted on the bus as `daemon.drain.roll_unsatisfiable`, naming the deadline count, the in-flight floor, how long the stalled **episode** has run (which spans ticks with nothing armed, so it is not the live roll's armed duration), and the three operator actions (`loom-daemon list` to find the long sweep, `loom-daemon cancel --sweep <id>`, or `restart --drain --force-after-timeout` to force through, which *does* cancel it). Deliberately as narrow as #8514: an episode only advances for a **relaunch** roll this daemon armed and labelled with an artifact target, so a `fleet drain` teardown (`then_exit`) and an operator's untargeted `restart --drain` are never abandoned by the loop — the daemon gives up on its own rolls, never countermands someone else's drain. That ownership test is enforced in **both** places that could break it: it runs ahead of the sticky unsatisfiability flag in `RollStallTracker::observe`, and the abandonment in `run_tick` re-tests it before reaching `DrainState::abort()`, so a drain armed *after* a declaration has latched is left alone rather than cancelled on the next tick. Both halves are load-bearing — `fleet drain` detects a remote refusal by observing `drain.draining == false`, so aborting an operator's teardown would leave the host running and read as a refusal nobody is told about — and each is pinned by a regression test that latches the declaration first and arms the foreign drain second. This does **not** make such a host able to update, and is not intended to: #8998's other two directions (age-excluding a long-running sweep from the drain condition; dropping the full-drain requirement for an artifact roll on a host whose sweeps are detached processes that survive a daemon restart) are the work that would, and both change safety-relevant semantics, so they get their own design pass rather than riding along here. The detector's state machine is pure and env-free (`loom-daemon/src/auto_update/roll_stall.rs`), so the whole arm/refuse/abandon/re-arm/supersede sequence is unit-tested rather than reproduced over 21 hours; the loop's four knobs are now bundled as `TickTuning` (`loom-daemon/src/auto_update/tuning.rs`) because two of the three it replaced were both `Duration` and a transposition at the call site would have compiled.

- **Clearing a stale review verdict now disarms GitHub's server-side auto-merge, not just the label** (#8900) — `verdict-staleness-guard.sh --clear` and `claim_reconciliation`'s daemon-native backstop invalidate a verdict (`loom:pr` → `loom:review-requested`) whenever a PR's head moves after a review, but neither one touched an auto-merge that had been armed earlier (e.g. by `merge-pr.sh --auto`, or an operator arm). An armed queue is gated **only** by the branch ruleset's required checks — it never re-reads labels, never notices the `loom:verdict-stale` comment, and never runs `merge-pr.sh`'s own #8248 required-check-freshness guard, which lives inside that script — so the label flip was cosmetic and the queued merge fired on the new, unreviewed head anyway. Observed live on 2026-09-25: #8694 merged as `528f2971` three minutes after a Doctor rebase force-push, still labeled `loom:review-requested` with no approval at the merged head; #8847 and #8843 merged ~2 minutes after `gh pr update-branch` moved their heads. Both verdict-invalidation paths now read the PR's auto-merge arm state and, if armed, send `disablePullRequestAutoMerge` **before** posting the audit comment and flipping labels — the safest of the three orderings, since a disarm can only prevent a merge, never cause one. The disarm is idempotent and a no-op unless something is actually armed, so an ordinary stale-verdict clear costs one extra read and the comment never claims a disarm that did not happen; a failed disarm does not block the clear but is recorded as a warning in both the comment and `REASON` so an operator knows a queued merge may still fire. It also runs on a PR an operator has explicitly held (`loom:operator`/`loom:blocked`) even though the label-clear itself stays suppressed there — an armed queue would merge a held PR anyway, which is the one write that would undo the hold rather than respect it — recorded in its own comment. New `loom-daemon forge disable-auto-merge <pr> [--audit-comment [--hold <label>]]` CLI verb (the disarm mutation, callable by hand or from either path) is deliberately **not** operator-gated, unlike its `forge auto-merge` inverse: it can only turn a queued merge off, never on, so there is no state in which calling it makes an unreviewed merge more likely. The mutation itself exists in exactly one place, `loom-daemon/src/forge_disable_auto_merge.rs`: the daemon's periodic pass calls it in-process (`loom-daemon/src/claim_reconciliation/auto_merge_disarm.rs`), and `verdict-staleness-guard.sh --clear` shells out to the CLI verb with `--audit-comment --hold "$HOLD_LABEL"` rather than mirroring it in shell — new executable logic belongs behind a `loom-daemon` subcommand (`.loom/docs/shell-language-policy.md`), and the shell-budget ratchet refuses the duplicate outright. A host that cannot resolve `loom-daemon` reports `AUTO_MERGE_DISARMED=0` with the reason named in `REASON=` rather than failing silently, and the clear itself still proceeds.

- **A platform symlink above the workspace root no longer fails every private-workspace export** (#8870) — #8830's export hardening walked **all** ancestors of a control-record destination and refused any symlink among them, including the ones the *platform* owns. On macOS that is unconditional: a default `TMPDIR` resolves through `/var -> /private/var` and `/tmp -> /private/tmp`, so `export::check_runtime` — which every dispatch calls before a runtime is admitted — bailed with `private export destination contains a symlink` on every call. The visible damage was not in the Codex path at all but in the **build gate**: `bash .loom/scripts/build-gate.sh` runs the Rust lib tests, two of which dispatch (`sweep_registry::model::dispatch_tests`), so on a macOS sweep host the gate failed for *every* builder on *every* issue regardless of its diff — releasing the claim (`loom:building` → `loom:issue`) with no PR opened, and pointing each builder in turn at private-workspace export rather than at its own change (the "main is broken" misread `builder.md` warns about after #5388). CI never caught it because GitHub's Ubuntu runners have a real `/tmp`. `safe_parent` now takes the caller's trusted root explicitly and walks only the components **below** it: the prefix up to and including the root is host-chosen (daemon `workspace_root`, or the `/workspace/repo` mount inside a private clone) and a symlink there is the platform's, while every component under it is worker-reachable and still refused — so a clone that plants `.loom -> /somewhere/host` cannot redirect a host-side write or read, which a test pins alongside the platform-prefix allowance. `strip_prefix` being lexical, a `..` component and a destination outside the root are refused by name rather than silently walking nothing, and `read_small` keeps its `O_NOFOLLOW` open as the race backstop. The allowance is scoped to a root, not a blanket "symlinks are fine now".

- **A multi-record log region's non-final launches are journaled instead of dropped** (#8659, split from #8633) — #8633 stopped a region's earlier launch being billed to whichever tap announced itself *last*, but the journal side kept calling the one-row `account_launch_log`, so in a multi-record region (a re-dispatch inside one sweep, a containment re-exec, or an orchestrated sweep whose phases pin their own runtime via `runtimes.rolePreference` / `LOOM_RUNTIME_<ROLE>`) the earlier launches were no longer *wrong* — they were simply absent from `loom-daemon sweep-outcomes summary --group-by tap`. A new `tap_usage::account_region_by_tap` returns the region folded to one row per tap (`RegionAccounting`), which resolves the two multi-record shapes differently and on purpose: a re-dispatch/re-exec that re-announces the **same** tap now journals the region's *whole* usage in the single `tap_usage` row (previously only its final block), while a genuinely multi-tap region keeps `tap_usage` naming the launch the outcome belongs to and carries every tap's folded share in a new `tap_usage_all` on `sweep-outcomes.jsonl`. Unlike taps are never merged into one row — that is the #8633 error restated — and an unattributable *last* record still declines the one-row attribution (an earlier launch is never promoted into "which tap did this sweep run on") while its measured spend is preserved in the breakdown. The `sweep.outcome` telemetry decision is made explicitly rather than by default: `config.tap` and its counters stay **one** tap, because that map is flat strings and `--group-by tap` puts a record in exactly one bucket, so a region a single tap cannot represent is *flagged* with a new `config.tap_region_keys` listing every tap in the region and broken out in full on the sibling journal line. Both new fields are written only when a single row is insufficient, so every single-tap record — the only shape observed on the fleet to date — keeps its exact pre-#8659 key set, and a pre-#8556 or pre-#8659 line still parses (`#[serde(default)]`, since `read_all` silently drops a line it cannot deserialize). Additive per #4703 — no `schema_version` bump.

- **Tap-attributed usage is sliced per launch record instead of folded onto a region's last tap** (#8633, a Judge finding on #8556's PR) — `tap_usage::account_launch_log` anchored its usage scan at the *dispatch header* and its attribution at the region's *last* `# LOOM_LAUNCH` record, so every launch in a multi-record region was billed to whichever tap happened to announce itself last. A region holding more than one record is not exotic: `api_keys_pool::ingest::parse_launch_record` already documents the re-dispatch and containment re-exec cases, and an orchestrated sweep whose phases spawn their own workers adds a third — `runtimes.rolePreference` / `LOOM_RUNTIME_<ROLE>` deliberately pins one phase (Judge, for review independence) to a *different* tap from the rest. The error was assumed conservative on the theory that the later launch is the metered backstop, so a misattribution would only overcount an already-metered tap; that theory does not survive the phase-pin case, because `runtime_preference` fixes fall-through at **dispatch** ("one sweep, one runtime") — a region's second record comes from a pin or a re-exec, not from a tier walk, so a metered builder followed by a subscription-pinned judge charged the metered tokens to the flat-rate tap, which is the one direction a fleet spend ceiling must never be wrong in. Now each `# LOOM_LAUNCH` line opens a block and only the usage events after it are charged to the tap it names; `account_launch_log` keeps its one-row contract (the region's last record, with **only its own** usage) and a new `account_launch_logs` returns every block in log order for a reader summing a whole region — feed it to `fold_by_tap` and each tap reports its own share. Usage appearing before a region's first record, and usage under an unattributable record, is charged to nobody rather than to a neighbouring tap, the same "no opinion rather than a fabricated reading" rule the rest of the module follows. Record lines are now matched line-anchored (as `parse_launch_record` matches them), so a transcript echoing `# LOOM_LAUNCH ` mid-line can no longer open a phantom block. Single-record regions — the overwhelmingly common shape — are unchanged, and the journal keeps storing exactly one row per sweep.

- **`loom-daemon fleet-config`: read an operator's fleet state store** — an operator can keep a whole fleet's desired state in one private GitHub repo (the repo roster and priorities in `repos.yml`, fleet-wide and per-host daemon config in `fleet/defaults.json` and `fleet/hosts/<host>/{defaults,local}.json`, and per-host run state in `fleet/state.yml`), and hosts read it straight from the forge. - **Operator-priority escalations now reach the operator in Matrix, not only as a GitHub comment** (#9321, the delivery half of #9244; follows #9301/PR #9320) — a starred (`loom:operator-priority`) issue that lands in a state only the operator can move has produced an idempotent forge comment, a `health`/`status`/`queue` row and a loom-ui row since #9301, and none of those is a notification. That is the #9268 failure mode restated: four agents commented on a stuck starred issue for seven hours and no human saw it. The star-liveness pass now also publishes **`operator_priority.escalation`** on the event bus, and the Safehouse narration sink relays it into the signal room — the notifications-on room the operator actually watches — as a `handoff` envelope prefixed with `safehouse.operatorMention` (`LOOM_SAFEHOUSE_OPERATOR_MENTION`), e.g. `@operator:example.org: loom#9268 · OPERATOR NEEDED · merge-refused at needs-operator` followed by the concrete ask, the issue link and the observing host. The watchdog stall (`no-progress`) rides the same path, since it is the same escalation call. **The new topic adds no second dedupe.** The notice is produced *by* the call that posts the forge comment and *only* when it posts, so the comment's `<!-- loom:operator-priority-escalation key=<kind>:<specifics> -->` marker — already the fleet's shared lock — is the only thing deciding "once": no repeat across ticks (the per-process ledger short-circuits), across hosts (a peer finds the marker and stays quiet), or across restarts (the marker is re-read). One un-pinged `operator ask resolved ✓` line follows when the key stops being asked — from the host that announced it, and never for a repo whose pass failed to read, because an unreadable repo must not read as "everything cleared". Escalation links are built from the repo's `origin` remote, so a Gitea fleet's line is clickable too. Degradation is unchanged in both directions: `safehouse.enabled` false (or an unreachable socket) leaves the comment and the status surfaces exactly as they were, and a missing `operatorMention` posts the ask without a ping rather than dropping it — `operatorMention` is a **handle, not a credential** (the persona authenticates; nothing here does), so it sits beside the room ids in config. The envelope deliberately carries **no `meta`**: envelope-v1 permits `meta` only on a `completion`, and `build_send_request` refuses it on anything else — during development that refusal silently ate the escalation at the last hop, reproducing the exact silence being fixed, so a test now asserts sendability rather than shape. Both envelope renderers moved out of `safehouse.rs` into a new `safehouse/envelopes.rs` (the file-size ratchet's intended path; the ledger drops), and the end-to-end coverage composes the **real** publisher with the **real** sink over a fake `safehoused` `AF_UNIX` peer, asserting exactly two sends (one ask, one recovery) across three ticks, a peer host and a restart. Documented in `defaults/docs/safehouse.md` § "Operator-priority escalations" and the `daemon-reference.md` event taxonomy.

- **`eta-explanation/v1` now carries `result.stage_marks`: the projected wall-clock time of every future stage boundary** (#9366) — the explanation could say what the estimate is (one terminal scalar, `result.eta_p50_at`) and how each stage distributes on the simulated path (`stages[]`, budget-droppable), but not "PR opens ~T1, approved ~T2, merged ~T3", which is what a per-item detailed timeline wants to draw. Each `StageMark` (`stage`, `p25_at`/`p50_at`/`p75_at`, `mean_visits`, one per stage in `Stage::ALL` order) is `as_of` plus that percentile of the stage's **cumulative entry time** over the paths `combination` already simulated — captured at each path's first visit of the stage without touching the generator, so seed, draw streams and every existing number are byte-identical; a client summing `stages[]` p50s would re-derive the conditioned inverse-CDF arithmetic and ignore the rework interleaving the simulation already ran, which is exactly what this spares it. The terminal stage's mark is the path **completion** time (its boundary is the estimate itself), so its `p50_at` equals `result.eta_p50_at` to the second — pinned by test for both heuristics; a stage no path visits carries `null` times and no `mean_visits`, never a fabricated value; and the list is self-contained (`mean_visits` mirrors the stage entry's), so a timeline renders from `stage_marks` alone. Under `enforce_cap` the marks drop as one named unit, `"result.stage_marks"`, in a tier of their own — `features`, then the grids, then the marks, then `detail` — so an ordinary features-only or grids-only truncation leaves the timeline intact and the terminal scalar survives every tier. - **The `forge.event` early-tick consumers are now measurable, and the second one is named for the loop it ticks** (#8995, Phase 2 follow-ups from the #8994 review; epic #8764 / ADR-0021) — four findings, none of which changes any loop's decision logic, threshold, or cadence constant. **(1) `queueHeadWake` became `claimReconcileWake`** (`LOOM_FORGE_EVENTS_CLAIM_RECONCILE_WAKE`), because the old key promised an effect it cannot produce: it ticks the claim-reconciliation pass, and releasing a dead `loom:building` claim does not itself move the dispatch queue's head — the work finder still has to tick before the freed issue is dispatched. - **Verified private-clone containment can admit Codex mutable roles, on measured evidence rather than on a capability flag** (#8787, phase 3 of the private-clone workstream under epic #4489; consumes #8785/#8786/#8839) — Codex's `worktreeIsolation` is `partial` because a host Codex worker shares the operator's checkout: `workspace-write` confines it to the workspace *root*, not to its own `issue-N` worktree. An **account-private clone** removes that premise rather than the symptom — no host checkout, sibling worktree or peer account repository is mounted anywhere in the container, and the whole clone at `/workspace/repo` is the worker's owned sandbox — so `loom-daemon` admission may now satisfy **the single requirement `worktreeIsolation`** for such a launch from a `ContainmentProof` instead of from the manifest. Nothing else moves: `defaults/runtimes/codex.json` still declares `worktreeIsolation: "partial"` / `hooks: "partial"`, ordinary host and shared-mount Codex admission is byte-identical (a unit test asserts the pre-#8787 refusal reason verbatim), no `runtimes.*` default changes, private sessions stay opt-in and default-off, and **#4496 remains the live production go/no-go**.

  **A proof cannot be configured into existence.** `ContainmentProof` has no public constructor, is neither `Clone` nor `Copy`, and is reachable by exactly two routes, both of which measure the running system: on the **host**, `dispatch::Selection::contain` — from a selection that already owns the exclusive account lease and its durable job identity — re-inspects the container by **immutable ID**, re-validates Docker's own settings/mount/ownership inventory, and re-observes the `loom-private-control-v1` boundary (#8839) inside the container, requiring it to hash to the identity bound at preparation; inside the **worker**, `containment::in_container` rebuilds it immediately before the model is exec'd from the bound identity the host wrote onto that container process with `docker exec --env`, cross-checked against the clone's own identity record, the container hostname, the read-only rootfs and an owned Git root with no object alternates. There is no skip flag, no trust bypass, no test-only environment variable and no container label anywhere on the path; `ContainmentProof::fixture` is `#[cfg(test)]` and compiles out of every shipped binary.

  **Containment replaces one obligation and proves the rest per launch.** A Docker boundary does not stop an authenticated force-push, so admission additionally requires that the clone actually *have* a managed registration (`bundle::Report::managed` — a clone shipping no Loom surface is refused for mutable roles) **and** that the account profile has established Codex hook trust, because an untrusted hook is read and then silently ignored by the pinned CLI, which makes "registered" not the same as "enforcing". That trust rule is #5005's install-time baseline diff, now implemented a second time in Rust (`containment::hook_trust_established`) for private sessions; a unit test runs the **shipped** `provision-codex-hooks.sh verify` against the same fixture profiles and asserts both gates return the same verdict, so the two can never drift into disagreeing about one profile. Because `hooks.json`, `config.toml` and `loom-codex-hooks.json` are all members of the bound control identity, the trust verdict is a pure function of state that is already re-hashed at spawn and at exec, so it needs no separate recheck. The full obligation-to-mechanism table, the supported image/CLI/protocol combinations, the remaining limitations and rollback are in `defaults/docs/guardrail-parity-codex.md` § "Verified private-clone containment".

  **One account selection, one lease, one launch.** Capability rejection happens *before* account selection on every path, so admission became two steps inside one decision: static admission runs unchanged, and only a rejection whose runtime is Codex and whose **sole** unmet capability is `worktreeIsolation` is eligible to ask a `ContainmentPreparer`. The preparer holds at most one #8786 `Selection` — the same one the launch uses, with the same exclusive lease; there is no second account-selection pass — and a candidate the ordered runtime-preference walk then passes over (unavailable pool, backstop ceiling, not the chosen tap) releases it before the walk continues. A contained admission that reaches the launch site *without* its selection is refused rather than silently re-prepared. An explicit operator pin still disables fall-through: containment may satisfy the pinned runtime's own requirement, never reroute to another one. The same shape is wired into unlocked sweep preparation, the role-runner tick, and direct adapter entry, and is repeated independently in-container by `private-workspace execute`.

  `spawn-codex.sh`'s mutable-role hook preflight is **relocated, not skipped**: the registration it would check names an image-owned bridge path that does not exist on the host, so verifying it there would evaluate the wrong bridge against the wrong workspace. The audit line reports `hooks=verified-in-private-session`, reachable only when a private account lease was inherited *and* session-exec mode is active — and `transport::run` now refuses outright to degrade a leased launch into a non-private exec, so the branch cannot be reached by setting a variable. `--dangerously-bypass-hook-trust` is still passed nowhere. Each admission records a secret-free `ExecutionProvenance` (mode, satisfied requirements, **the manifest's own native values for those requirements and for `hooks`**, policy, account name, short container and control identities, protocol, base revision) behind the greppable `# LOOM_RUNTIME_CONTAINMENT ` marker, persisted beside the durable job and surfaced by `accounts session status --json`; carrying the native values inline is what stops a contained admission being read back as native hook parity.

  Evidence: 19 new unit tests plus two disposable-Docker integration tests driving the production preference resolver and the real adapter chain — bare-host, unmanaged-clone, untrusted-profile and replaced-container sessions each refused with their own obligation text, and a verified session running a mutable role whose issue-branch commit and push land while the protected remote ref, the host checkout, the host sibling directory and the peer account's profile and volume are all unchanged.

A genuinely session-global `CARGO_TARGET_DIR` is still honored for the main workspace, unchanged. Both, plus the no-lib degraded path, are pinned by new cases in `tests/hooks/test-post-worktree-target-dir.sh`.

  Two attribution rules are relaxed, for these directories and only these: containment stops counting as sharing (the per-worktree dir lives *under* the shared root by design, so the primary checkout is always a containing "sharer" — without this nothing would ever be reclaimed), and a machine-global *source* no longer refuses a value carrying the per-worktree shape (the spawn path puts that value in exactly the `CARGO_TARGET_DIR` gate 2f guards against). Both are gated on a purely **structural** predicate — the path must end in `/wt/<the removed worktree's own directory name>` — so matching it is itself the attribution: a shared root can never satisfy it, and a corrupt or hand-edited marker can only ever name `<something>/wt/<this worktree's own name>`, never the shared root, a parent of it, or a sibling's dir. The #7239 data-loss guards are re-asserted with the feature ON in `defaults/scripts/tests/test-per-worktree-target-dir.sh` (41 cases) and `cargo_target/per_worktree.rs`.

  **Default OFF, deliberately.** Per-worktree dirs also stop sharing third-party `deps/`: nearly free when the host runs a `rustc-wrapper` (sccache keys on inputs, not on Cargo's path hash — the configuration #8453 measured), and a fleet-wide rebuild storm when nothing does, which *is* #6013/#6014. It is the operator's switch, on the same host where the shared `build.target-dir` was configured. On a host with **no** redirect it is a no-op even when enabled — `<worktree>/target` is already per-worktree and is removed with the worktree, so nothing is relocated. Does not retroactively clean directories already orphaned inside a shared root (a GC pass is #8459). Documented in `defaults/docs/troubleshooting.md` → "Per-worktree cargo target dirs".

New hermetic suite `test-curator-rightsizing.sh` pins each load-bearing clause in both prompts and their generated agent skills.

- **The real Codex engine is now shown to dispatch to Loom's guard hook, with real operator-established trust, instead of that being inferred** (#8839, third increment; follows #8854's image-owned bundle and #8864's mount-frozen registration) — both earlier increments proved the bridge denies when it is *run* and that the registration the CLI *would* read names the image-owned copy; neither showed the engine invoking it, which acceptance criterion 3 asked for and both deliberately left open as needing "a model turn, i.e. credentials". It does not: §12 of `docker/session/test-image.sh` now drives the real `codex exec` from the shipped image against a **scripted loopback model provider** — a ~30-line Node server on `127.0.0.1`, in a `--network none --read-only --cap-drop ALL` container as uid 1000, with the profile's three control files bound read-only exactly as a session binds them and a local bare repo as the "remote". No account, no token, no model call, nothing to leak. **Hook trust is real, not waived**: Codex persists it only through an interactive TUI decision, so the probe makes that decision the way an operator does — it runs the shipped TUI under `tmux` with the profile still writable (the same pre-session step `provision-codex-hooks.sh` documents), waits for the "Hooks can run outside the sandbox" prompt *by its text*, and answers it. Nothing writes a `trusted_hash` by hand, and `--dangerously-bypass-hook-trust` is now passed nowhere at all — neither in shipped Loom code nor in Loom's own tests — so what is measured is the production path exactly as it runs. Two profiles are provisioned and registered identically and differ **only** in the answer to that one prompt (`2` trust-all vs `3` continue-without-trusting, asserted via the presence and absence of `hooks.state…trusted_hash`), and the identical probe runs against each: a force-push over the protected ref is **blocked by the engine** carrying the guard's own reason and the bare repo's `main` never moves; a benign write through the same live hook **runs**, so the block is a decision rather than a blanket refusal; and the identical force-push in the untrusted profile runs **unhooked** and **lands**, which is both the control that makes the first result non-vacuous and the executable form of the fail-open finding #8854 documented (an untrusted hook is skipped with no error, no warning and no `doctor` finding). An always-allow recorder hook registered beside Loom's — before the trust step, so trust-all covers it too — captures what the engine actually delivers, and the shape is asserted: **0.149.1 emits `tool_name: "Bash"` with `tool_input.command` as a string**, not the `shell` + argv array the bridge's 0.146.0 schema documents and every fixture used. `guard-codex-bridge.sh` already handled both, so no bridge change was needed — but `loom-daemon/tests/private_workspace_docker::control` now drives **both** shapes through the image-owned bridge for the same escalation, so the synthetic layer can no longer diverge from the engine's own payload unnoticed. The turns also prove a non-regression nothing else covered: the real CLI runs normally with `hooks.json`, `config.toml` and `loom-codex-hooks.json` frozen as read-only mount points. No capability promotion (`hooks` stays `partial`), no fleet enablement; **#4496 remains the live production gate**. See `defaults/docs/private-control-bundle.md` § "The engine really does dispatch to the hook — measured, not inferred".

- **A private Codex session's hook registration and Codex trust state are now immutable from inside it** (#8839, control protocol `loom-private-control-v1` **v2**; follows #8854's image-owned guard bundle) — #8854 moved every guard *script* onto the session image's read-only rootfs, but the file that tells Codex to run them, `$CODEX_HOME/hooks.json`, stayed in the read-write account profile, as did Codex's own `hooks.state` trust in `config.toml` and Loom's readiness receipt. Those three were **detected** on change at the next recheck and nothing more, which leaves a real window: remove the registration after the pre-exec recheck and every remaining turn of that session runs unhooked, with nothing re-reading the file until an admission that comes long after the unhooked turns. The host now binds each of the three **read-only over its own canonical path**, so each is a *mount point*: a write is `EROFS`, an `unlink` or a `rename` (in either direction) is `EBUSY`, and `ln -sf`/`ln -f` over it is `EEXIST` — while the profile **directory** stays read-write, which is what keeps the canonical atomic `auth.json` refresh (write a sibling temp, rename over) working untouched. File modes cannot express this: directory write permission is exactly what governs `unlink`/`rename`, and the directory has to stay writable for authentication. Both halves are enforced independently, so neither side has to be believed — the host checks Docker's own mount inventory on every admission (exact mount count, so a *missing* protection is refused as loudly as a wrong one), and the container requires both an entry in the kernel's `/proc/self/mountinfo` naming that exact path with `ro` **and** a real open-for-append that actually fails, reporting the new `profile-mutable` status and binding no identity when it cannot prove both. Because a session cannot provision what it is forbidden to write, `session start` now runs the image's own **sealed** provisioner in a throwaway container carrying nothing but the account profile (no workspace volume, no forge configuration, `--network none`, `auth.json` never read) *before* creating the session; an already-correct profile is left byte-for-byte alone, and in-session `setup` skips hook provisioning entirely once it measures the controls as protected. `CONTROL_VERSION` is **2**, so a v1 image — whose in-container half cannot make this claim at all — is refused rather than silently accepted, and an existing session must be stopped and started again to gain the protection (there is no way to add a mount to a running container). Proven end-to-end in `private_workspace_docker::control` against a real session: every escalation route tried file-by-file, the same routes shown to still succeed against an unprotected profile so the closure cannot be vacuous, and the atomic auth refresh asserted in the same breath. `docker/session/test-image.sh` makes the same claims against the real shipped image. No fleet enablement; **#4496 remains the live production gate**. See `defaults/docs/private-control-bundle.md` § "The hook registration and the profile's trust state are immutable from inside".

- **Every Loom-spawned worker now builds with `CARGO_INCREMENTAL=0`** (#8456, parent #8453 item 1) — the daemon dispatcher's env seam (`worker_spawn::run`, alongside `LOOM_RUNTIME` and the #8077 isolation defaults) injects it for every dispatch surface (sweep dispatch, role-runner children, manual `spawn-worker.sh`) and every runtime adapter, native harnesses and legacy shell adapters alike; dispatch paths that cross a docker boundary carry it across explicitly, since neither `docker run`'s by-name passthrough nor `docker exec` forwards it on their own (`spawn-claude.sh`'s containment env exports it next to `CARGO_TARGET_DIR`; `spawn-codex.sh`'s session-exec wraps the CLI in `docker exec -e CARGO_INCREMENTAL=0`). On a host that points every checkout at one shared cargo target directory with `rustc-wrapper = "sccache"` configured, incremental compilation was the worst of both worlds: an incrementally-compiled crate is **non-cacheable by sccache**, so workspace crates never hit the cache — and cargo keys a crate's incremental session state by its **absolute source path**, so with every Loom worktree a new path, the state written under a discarded worktree is never reused and never cleaned (213 GB across 6,402 orphaned session dirs measured on one fleet host). The default is unconditional by design (an inherited `CARGO_INCREMENTAL=1` would silently re-enable both failure modes) but spawn-time only — an operator's interactive shell and manually-run `cargo build` are unaffected, and a worker can still opt a single command back in with an inline `CARGO_INCREMENTAL=1 cargo …` prefix. Documented in `defaults/docs/build-gate.md` → "Worker builds run with `CARGO_INCREMENTAL=0`" and `defaults/docs/runtime-adapters.md`'s dispatcher-env section.

### Changed

- **`uninstall-loom.sh`'s orphan-worktree `rm -rf` fallback no longer decides by parsing git's error text** (#6159, check-in on #5999, PR #6701) — the fallback that deletes a `.loom/worktrees/<entry>` git refuses to remove was gated solely on the substring `is not a working tree` appearing in `git worktree remove`'s stderr. git makes no compatibility promise about that wording, and it was the only thing standing between a live worktree and an unconditional recursive delete (the specific fear in Champion's merge hold on #5999). It now asks `git worktree list --porcelain` — a documented plumbing interface — whether the path is registered, and additionally requires the path to resolve strictly inside `.loom/worktrees/`; the `rm -rf` fires only when both hold. This is a stricter guard than the daemon-side `should_force_remove_orphan_dir` (`loom-daemon/src/worktree_ops/clean.rs`), which still gates on the error string (`is_untracked_worktree_error`) ANDed with a `.loom-managed` sentinel and a containment check: the uninstall predicate does not read the error text at all, so it cannot be fooled by a rewording in either direction. The membership query itself **fails closed** — if `git worktree list --porcelain` cannot be answered (transient I/O error, lock contention on `.git/worktrees/` metadata, permissions, repo corruption), the path is treated as registered and preserved, since an errored query produces the same empty output as a genuine non-match and must never be read as "this is an orphan". Behavior under git 2.55 is unchanged for every orphan shape reachable today; what changes is that a future git rewording the message can no longer flip the classification in either direction. `defaults/scripts/tests/test-install-reinstall-safety.sh` Group 6 gains five cases, including one that pins git's actual error wording against the real binary (the string is still parsed by `defaults/scripts/worktree.sh` and `clean.rs`, so a git upgrade now breaks CI instead of silently changing field behavior), one that runs the uninstall under a shim git whose message has been reworded, and one (Case 8) that runs it under a shim git whose `worktree list --porcelain` fails outright, asserting a registered, locked worktree survives.
- **The Curator role now selects issues oldest-first, structurally rather than advisorily** (#6642, PR #6689) — the Priority 1 (`loom:issue` awaiting curation) and Priority 2 (`loom:triage`, then the unlabeled fallback) `gh issue list` queries in `defaults/.claude/commands/loom/curator.md` never fetched `createdAt` and never sorted; `gh issue list`'s undocumented empirical ordering is newest-first, so an active Curator working strictly off query order aged old raw issues indefinitely behind a stream of newer ones (observed: 3-day-old issues left un-curated while same-day issues were curated), which is indistinguishable from a dead Curator to an external fleet-health check watching raw-issue age. ### Fixed

- **A worktree's REDIRECTED cargo target dir is now reclaimed when the worktree is removed** (#7239, PR #7251) — Cargo's build output is only `<worktree>/target` by default; `CARGO_TARGET_DIR` or `build.target-dir` in any `config.toml` on the lookup path (the shape `/repo:host-optimize` documents) redirects it outside the worktree, where **no** removal path ever looked. `.loom/scripts/worktree.sh remove`, `merge-pr.sh`'s post-merge cleanup, `loom-daemon clean`, and the daemon's periodic worktree reaper all only ever touched `<root>/target` literally, so every redirected per-worktree target dir outlived its worktree indefinitely — one multi-agent host accumulated tens of orphaned directories and hundreds of GB on an external volume before the pressure surfaced. All removal paths now resolve the *actual* target dir **before** removing the worktree (`cargo metadata`, so the whole config hierarchy is honored — new `defaults/scripts/lib/cargo-target-dir.sh` on the bash side, `loom-daemon/src/worktree_ops/cargo_target.rs` on the Rust side, both parity-tested against the existing `scripts/cargo-target-dir.sh` so they cannot drift) and reclaim it **after** the worktree is off disk. It is never removed when another live worktree resolves to the same directory (the single-shared-`target-dir` convention — containment counts in both directions, and an unanswerable sharing question, i.e. a failed `git worktree list`, refuses rather than assuming "unshared"), when a running process is using it (same evidence-based gate as #6127), or when it resolves to the repository itself, an ancestor of it, the primary checkout's own `target/`, `$HOME`, or a suspiciously shallow path; each refusal is reported with its reason. One attribution rule keeps a *machine-global* cache out of the blast radius: **only a redirect derived from the worktree itself — `build.target-dir` in a `.cargo/config.toml` inside it — can be evidence that a directory belongs to it.** Four inputs look like such evidence and are not, and each one deleted a shared cargo cache in a review reproduction: a worktree with no `Cargo.toml` at all (the manifest pre-check now runs **before** the `CARGO_TARGET_DIR` short-circuit, so a tree that never built with cargo resolves to its own in-worktree `target/`, exactly as the sharing scan already judges every *other* worktree); the remover's own ambient `CARGO_TARGET_DIR` (read from the removing process's environment, machine- or session-global by construction); a `build.target-dir` in `$CARGO_HOME/config.toml` or in an ancestor `.cargo/config.toml` above the worktree (equally global — the redirect pre-check consults only the worktree's own config files, and the reclaim step additionally refuses a path that merely equals a machine-global value); and a *degraded* resolution of some other live worktree (when `cargo metadata` fails for a sibling the resolver falls back to `<sibling>/target`, so a real sharer stops looking like one — the sharing scan now fails closed on that exactly as it does on a failed `git worktree list`). `worktree.sh remove --dry-run` (new) and `loom-daemon clean --dry-run` list the reclaimable directories with sizes and change nothing. Un-redirected hosts are unaffected and pay no added cost: a cheap pre-check skips the `cargo metadata` invocation entirely unless a redirect is actually configured. The reclaim resolves what Cargo *would* resolve at removal time and never deletes by name/pattern, so a redirect visible only inside a build's own environment (a per-invocation `CARGO_TARGET_DIR`) is deliberately left alone rather than guessed at; directories orphaned before this landed still need removing by hand. Documented, with both caveats, in `defaults/docs/troubleshooting.md` → "Redirected cargo target dirs are reclaimed with their worktree".

## [0.18.0] - 2026-08-03

### Summary

Minor release in which the fleet becomes **self-repairing and self-shipping**. Loom
now ships **prebuilt `loom-daemon` artifacts** for every target platform — this is
the first release to exercise that pipeline, with checksums always, keyless Linux
signing via GitHub OIDC, and macOS signing gated on secrets that skip loudly when
absent (`daemon-update` treats an unsigned artifact as acceptable and fails only on a
*present but invalid* signature; artifact fetch stays opt-in, so source-build
self-update is unchanged). Alongside it: orphaned process trees left behind by dead
sweeps are now reaped, restart-adopted sweeps stop losing their outcome telemetry, the
watchdog and the supervised restart primitive become honest on both launchd and
systemd, agents get an ETag-cached forge listing surface and a REST fallback for issue
creation so GraphQL exhaustion no longer halts them, and the dashboard stops counting
hosts it has no health data for. 151 commits since 0.17.0, no breaking changes.

## [0.2.0] - 2026-01-24

### Summary

This release introduces the **Three-Layer Architecture** with the new `/loom` daemon as the centerpiece. Loom has evolved from a manual orchestration tool to a fully autonomous development system capable of generating its own work, scaling shepherds, and maintaining continuous operation.

### Architecture

#### Three-Layer Orchestration Model

Loom now operates across four distinct layers:

- **Layer 3: Human Observer** - Oversight, proposal approval, and strategic direction
- **Layer 2: Loom Daemon (`/loom`)** - System-wide orchestration and work generation
- **Layer 1: Shepherds (`/shepherd <issue>`)** - Per-issue lifecycle orchestration
- **Layer 0: Workers** - Single task execution (Builder, Judge, Curator, Doctor, etc.)

#### Role Restructuring

- Renamed `loom.md` to `shepherd.md` (now Layer 1)
- Created new `loom.md` for Layer 2 daemon role
- Updated all command references and documentation

### Added

#### Fully Autonomous Daemon (`/loom`)

- Continuous loop with configurable polling interval (default 30 seconds)
- Auto-spawns shepherds when `loom:issue` issues are available
- Auto-triggers Architect/Hermit when issue backlog falls below threshold
- Auto-ensures Guide and Champion roles keep running
- State persistence in `.loom/daemon-state.json` for crash recovery
- Graceful shutdown via `.loom/stop-daemon` signal file

#### Status Observation (`/loom status`)

- Read-only Layer 3 observation interface
- Shell script helper: `.loom/scripts/loom-status.sh`
- JSON output option for scripting and automation
- Shows shepherd assignments, issue counts, and daemon health

#### Cleanup Mechanisms

- Task artifact archival (`./scripts/archive-logs.sh`)
- Safe worktree cleanup (`./scripts/safe-worktree-cleanup.sh`)
- Event-driven cleanup (`./scripts/daemon-cleanup.sh`)

#### Resilience Features

- Stuck agent detection and recovery system
- Circuit breaker pattern for daemon IPC resilience
- Automatic recovery from `daemon-state.json` on restart

#### Observability

- Agent effectiveness metrics tracking
- LLM resource usage tracking (tokens and cost)
- Test outcome tracking in activity database
- Prompts linked to GitHub issues, PRs, and commits

#### Builder Enhancements

- Parallel claiming workflow for faster issue claiming
- Pre-implementation review section in role guidelines
- Worktree merge graceful handling

#### Other Features

- Auto-configuration of missing terminals in force mode
- Graceful shutdown signal script for Loom agents
- Dependency unblocking in Guide role
- Auto-unblock for dependent issues when Champion merges PR
- Extend command to claim system for long-running work
- CLI fallback mode for `/loom` orchestrator when MCP unavailable

### Changed

- Documentation updated to reflect three-layer architecture
- Clarified daemon execution model: background process vs interactive mode
- `/loom --force-merge` now runs Judge phase instead of skipping

### Fixed

- Worktree merge handling in Loom orchestrator
- Force-merge mode properly runs Judge phase

### Configuration

|-----------|---------|-------------|
| `ISSUE_THRESHOLD` | 3 | Trigger Architect/Hermit when `loom:issue` count below this |
| `MAX_PROPOSALS` | 5 | Maximum pending proposal issues |
| `MAX_SHEPHERDS` | 3 | Maximum concurrent shepherd processes |
| `ISSUES_PER_SHEPHERD` | 2 | Scale factor: target = ready_issues / ISSUES_PER_SHEPHERD |
